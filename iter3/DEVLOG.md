## 2026-08-25 (화) — [iter3] 5차 평가 피드백: 펀치 시 후진 재발 · 회전 제어

### [20:30] 펀치 시 뒤로 밀리는 문제 재발 — 잠금에 뚫린 구멍 3개

3차에서 넣은 `PUNCH_LOCK`이 막지 못하는 경로가 세 개 있었다. 하나씩 막았다.

**(1) 중립 기준 보정이 잠금과 무관하게 돌고 있었음**

```js
// 문제: postureLocked 여부를 보지 않는다
if (neutral.ready && !punch && Math.abs(sPitch) < 0.05 && ...) {
  neutral.faceRel += (faceRel - neutral.faceRel) * a;   // faceRel = 펀치로 흔들린 생값
```

잠금 중에는 `sPitch`가 0으로 얼어 있어 위 조건이 **항상 참**이 된다. 그런데 갱신에 쓰는
`rollRaw`/`faceRel`/`shMidY`는 얼지 않은 **생값**이라, 펀치할 때마다 중립 기준이 펀치 자세 쪽으로
끌려갔다. 누적되면 진짜 정지 자세가 "기울어진 것"으로 읽힌다.
→ `!postureLocked` 조건 추가.

**(2) 고정 480ms로는 팔이 다 돌아오기 전에 잠금이 풀림**

뻗은 팔이 회수되는 중에 잠금이 풀리면 그 자세가 그대로 신호에 들어간다.
→ **팔이 실제로 회수될 때까지 연장**한다(`PUNCH_LOCK_MAX` 1100ms 상한).
   판정은 손목 속도 > 0.9 m/s 또는 뻗음 > 어깨폭 1.0배.

**(3) [핵심] 감지되지 않은 펀치·헛펀치는 애초에 잠금이 걸리지 않음**

임계값에 못 미친 펀치, 페인트, 그냥 몸을 트는 동작도 **투영 어깨폭을 줄인다.**
잠금은 발동한 펀치만 보호하므로 이 경로는 무방비였다. 구조로 막았다.

- **얼굴·주먹의 어깨선 대비 상하 이동만이 방향을 결정한다**(`dirCore`).
  이 신호는 몸통이 돌아도 거의 변하지 않아 가장 신뢰할 수 있다.
- **어깨폭·상체하강은 보조**로 강등. 방향이 확실할 때(`conf`)만, 그리고 **부호가 일치할 때만** 기여한다.
  몸통만 트는 동작은 `dirCore`가 0 근처라 `conf`가 낮아 어깨폭 항이 걸러진다.
- 길이 단위를 순간 어깨폭 → **평활된 `sScale`(`uScale`)** 로 교체. 순간 어깨폭을 분모로 쓰면
  몸통 회전 시 얼굴·주먹 비율까지 함께 부풀려져 방향 판정이 오염된다.
- 어깨폭 추종을 **비대칭**으로. 몸통 회전은 투영 폭을 **줄이기만** 하므로,
  커질 때 빠르게(0.12s) / 작아질 때 느리게(0.45s) 따라가면 회전 오염만 골라 걸러낸다.

**효과 (깊은 몸통 회전 22% 축소 시 pitch 실측)**

| 구성 | pitch | BACK(-0.12) |
|---|---|---|
| 이번 라운드 이전 | **−0.13** | 발동 (드리프트 0.632) |
| + 어깨폭 비대칭 추종 | −0.04 | 안전 |
| + `uScale` 분모 | −0.06 → −0.04 | 안전 |
| **현재(전부 적용)** | **−0.01** | 안전 (드리프트 0.000) |

### [20:30] 회전 — 속도 축소 + 제스처당 45° 제한

- **증상**: 주먹을 옆으로 두면 계속 누적 회전해서 제자리에서 한 바퀴 돈다. 제어 불가.
- `ROT_SPEED` 3.4 → **1.3 rad/s**(≈75°/s).
- 제스처가 시작된 시점의 yaw를 **앵커**로 잡고 `±ROT_LIMIT`(**45°**) 안으로 clamp.
  더 돌리려면 주먹을 중앙으로 되돌려 제스처를 끝냈다가 다시 밀어야 한다.
  → 45°씩 끊어서 도는 제어 가능한 조작이 된다.
- HUD `Turn` 줄에 현재 회전량을 `nn/45deg`로 표시.

**실측**: 제스처를 3초간 유지 → 이전 152.4° 폭주 → 현재 **45.3°에서 정지**.
제스처를 끊고 다시 하면 추가로 44.7° 회전.

`pose_harness.js` 43 → **51개 전부 통과**. 추가 항목:
- `6-punch combo never triggers BACK` / `causes no drift` — 연타 시 중립 드리프트
- `undetected twist never triggers BACK` / `causes no drift` — **감지 안 된 몸통 회전**

## 2026-08-25 (화) — [iter3] 4차 평가 피드백: 전진 모션이 발동하지 않음

### [19:20] 원인 — 대칭 항을 통째로 빼버린 것이 과했음

- **경위**: 후진을 고치면서 `bodyDrop`(상체가 화면에서 내려간 정도)이 **방향에 대칭**이라는 이유로
  **완전히 제거**하고 어깨폭(카메라 거리) 항으로 대체했다. 그런데 이 항이 원래 **전진의 주력 신호**였다.
- **남은 어깨폭 항의 한계**: 카메라에서 조금 떨어져 서 있으면, 앞으로 숙여도 겉보기 어깨폭이 거의 안 바뀐다.
  게다가 몸통이 조금만 틀어져도 투영 폭이 줄어 상쇄된다. 그 결과 전진 점수가 임계값에 못 닿았다.
- 실제로 "제자리에서 숙이되 카메라에는 거의 안 다가가는" 자세(어깨폭 +2%)를 넣어보면
  `0.45·0.20 + 0.25·0.15 + 1.4·0.02 = 0.156` — 임계값 0.18 미달. 하니스로 재현 확인.

### [19:20] 수정 — 대칭 항을 "방향 결정"이 아니라 "증폭"에만 쓴다

두 항의 성질이 다르다는 점을 구조로 반영했다.

```
dirTerm   = 0.45·얼굴 + 0.25·주먹 + 1.20·어깨폭증가율     ← 반대칭. 방향을 결정한다
bodyBoost = conf · 0.30 · max(0, 상체하강)                ← 대칭. 방향은 못 정하므로 키우기만 한다
pitch     = dirTerm + bodyBoost
conf      = clamp01(dirTerm / 0.08)   // 부호 경계에서 튀지 않게 부드럽게 켜짐
```

- **전진**: `dirTerm > 0`이므로 `bodyBoost`가 온전히 실린다 → 예전처럼 주력 신호로 동작
- **후진**: `dirTerm < 0`이면 `conf = 0` → `bodyBoost`가 **아예 0**. 더 이상 후진을 상쇄하지 않는다
- 대칭 항을 빼지도, 그대로 더하지도 않고 **부호가 이미 정해진 뒤에만 기여**하게 한 것이 요점이다.
- 전진 임계값도 `0.18 → 0.16`으로 소폭 완화.

**효과 (하니스 실측)**

| 자세 | face | fist | body | near | 합계 | 판정 |
|---|---|---|---|---|---|---|
| 얕은 전진(카메라 접근 거의 없음) | +0.09 | +0.04 | **+0.07** | +0.02 | **+0.22** | FORWARD (임계 +0.16) |
| 후진 | −0.06 | −0.04 | **0.00** | −0.07 | **−0.16** | BACK (임계 −0.12) |

후진에서 `body` 항이 정확히 0으로 빠지는 것이 이번 설계의 핵심이다.
직전 버전은 여기서 `+0.02`가 더해져 마진을 깎아먹고 있었다.

### [19:20] pitch 항별 내역을 HUD에 노출

임계값을 다시 만질 때 추측하지 않도록, `pitch = face + fist + body + near` 내역과
필요 임계값을 HUD에 상시 표시하도록 했다. 어느 항이 부족한지 바로 보인다.

```
Pitch: 0.22
  pitch= face 0.09 + fist 0.04 + body 0.07 + near 0.02
  need : fwd +0.16  back -0.12
```

### [19:20] 검증

`pose_harness.js` 41 → **43개 전부 통과**. 추가 항목:
`shallow forward lean -> FORWARD` / `shallow forward lean walks forward (+X)`
— 카메라에 거의 다가가지 않는 전진 자세를 모델링한 것으로, **직전 공식으로 돌리면 `NONE`이 나와
실패하는 것을 확인**했다(증상 재현). 후진·펀치 잠금·근접 교전 등 기존 항목은 모두 유지.

## 2026-08-25 (화) — [iter3] 3차 평가 피드백: 펀치할 때 뒤/옆으로 밀리는 문제

### [18:40] 원인 — 펀치의 몸통 회전이 "카메라에서 멀어짐"으로 읽힘

- **증상**: 펀치를 치면 캐릭터가 뒤로 밀린다. 훅이면 좌/우로도 흔들린다.
- **원인**: 직전 수정에서 앞/뒤 판정의 세 번째 항을 **어깨폭(= 카메라 거리)** 으로 바꿨는데,
  펀치는 어깨를 넣는 **몸통 회전(yaw)** 을 동반한다. 몸통이 돌아가면 어깨선이 카메라에 비스듬해져
  **투영 어깨폭이 줄어든다.** 이것이 `nearDelta < 0` → "멀어짐 = 후진"으로 읽혔다.
  - 어깨폭이 12%만 줄어도 `1.4 × (−0.12) = −0.168`. 후진 임계값이 −0.12이므로 곧바로 넘는다.
  - 후진 발동을 위해 임계값을 낮춘 것(−0.18 → −0.12)이 이 오검출을 더 쉽게 만들었다.
  - 훅은 어깨선 자체가 기울어 `roll`도 흔들리므로 좌/우 스텝까지 유발한다.
- **직전 수정의 한계**: `PUNCH_FREEZE`(320ms)는 **적용(이동)만** 막았을 뿐,
  그 사이에도 `sPitch`/`sRoll`/`sShift`는 계속 적분되고 있었다.
  그래서 잠금이 풀리는 순간 그동안 쌓인 값이 그대로 튀어나가 뒤/옆으로 밀렸다.
  **적용을 막는 것만으로는 부족하고, 신호 자체를 얼려야 한다.**

### [18:40] 수정

- `PUNCH_FREEZE`(320) + `ROT_LOCK_AFTER_PUNCH`(500)를 **`PUNCH_LOCK`(480) 하나로 통합**.
  이 시간 동안 다음을 모두 정지한다:
  1. **자세 신호 갱신 정지** — `sRoll`/`sPitch`/`sShift`/`sScale`을 직전 값으로 고정.
     펀치의 과도 성분이 애초에 신호에 들어가지 않는다
  2. **이동·회전 상태 후보 차단** — 앞/뒤/좌/우/회전 어느 것도 새로 생기지 않는다
  3. **강도 즉시 0** — 잠금 직전에 남아 있던 상태의 속도도 바로 죽인다
  4. **적용 정지** — 기울임 이동·회전·근접 접근을 모두 건너뛴다
- 어깨폭에 전용 평활(`SCALE_TAU` 0.15초)을 추가해 lite 모델의 어깨폭 노이즈를 억제.
  단 잠금 중에는 이 평활도 갱신하지 않으므로 펀치 과도 성분은 아예 유입되지 않는다.
- 자동 조준 회전은 유지 — 제자리에서 상대를 향하는 것은 자연스럽고 타격 판정에 필요하다.

## 2026-08-25 (화) — [iter3] 2차 평가 피드백 반영 (후진 · host 펀치 표시 · 근접 교전 · 펀치 중 고정)

### [17:50] 후진 모션이 발동하지 않던 원인 — pitch 항 하나가 방향에 대해 대칭이었음

- **원인**: `pitch` 점수의 세 번째 항이 "상체 전체가 화면에서 내려간 정도"였는데,
  이 신호는 **앞/뒤에 대해 대칭**이다. 엉덩이를 축으로 어느 쪽으로 기울든 머리 높이는 똑같이 낮아지고,
  화면상 어깨선도 아래로 내려간다. 결과적으로 이 항이 **전진에는 가산되고 후진에는 상쇄**되어
  후진만 임계값에 닿지 못했다.
- 실제 후진 자세를 수치로 넣어보면(어깨폭 0.20→0.188, 어깨선 0.45→0.47, 얼굴·주먹은 어깨 대비 상승):
  `0.45·(−0.132) + 0.25·(−0.148) + 0.30·(+0.106) = −0.064` — 임계값 −0.18의 3분의 1 수준.
- **변경**: 세 번째 항을 **카메라와의 거리**(어깨폭 = 원근 스케일)로 교체.
  가까워지면 `+`, 멀어지면 `−`로 **반대칭**이라 방향 판별에 실제로 기여한다.

  ```
  pitch = 0.45·(얼굴이 어깨 대비 내려간 정도)
        + 0.25·(주먹이 어깨 대비 내려간 정도)
        + 1.4 ·(어깨폭 증가율 = 카메라에 가까워진 정도)
  ```

- **비대칭 임계값**: 사람은 앞으로는 크게 숙일 수 있지만 뒤로는 균형상 조금밖에 못 젖힌다.
  대칭 임계값 자체가 후진에 불리하므로 뒤쪽을 낮췄다 — 전진 `0.18/0.11`, 후진 `0.12/0.07`.
- 하니스의 후진 테스트도 **실제 카메라에 보이는 대로**(젖혀도 어깨선은 아래로) 다시 모델링했다.
  기존 테스트는 "젖히면 어깨선이 위로 올라간다"는 틀린 가정이라 버그를 못 잡고 통과했었다.
- 영향: `server/templates/fighter_client.html`

### [17:50] host UI에서 펀치가 보이지 않던 원인 — 가드가 펀치 포즈를 덮고 있었음

- **먼저 전송 경로부터 검증**: 실제 FastAPI 앱을 띄우고 가짜 `host_arena`·`client_1`·`client_2`를
  진짜 WebSocket으로 붙여 펀치를 보내는 종단 간 테스트를 작성(`e2e_punch.py`).
  → **5종 펀치 전부 host 소켓에 도달하고 `hits`까지 정상 첨부**됨. 네트워크 경로는 문제 없음.
- **진짜 원인**: `humanoid.js`의 포즈 선택 우선순위.

  ```js
  if (S.guard > 0.3) target = POSES.guard;          // 가드가 먼저
  else if (S.punch > 0.2) target = POSES.punchR;    // 펀치는 도달 불가
  ```

### [16:40] 펀치 인식 실패 원인 규명 및 수정

평가 피드백: **펀치가 잘 인식되지 않음**. 원인을 4가지로 분리해 각각 대응했다.

**(1) [핵심] 판정 3조건이 같은 프레임에 겹쳐야 했던 구조**

기존 `tryPunch()`는 `속도 > 2.0` ∧ `뻗음속도 > 0.7` ∧ `뻗음 > 0.38m`을 **한 프레임에서 동시에**
만족해야 발동했다. 그런데 펀치 신전 구간은 0.15초 안팎이라 15fps에서는 2~3 샘플뿐이고,
**속도가 최고인 프레임은 아직 덜 뻗었고 / 다 뻗은 프레임은 이미 감속**해서 양쪽 다 탈락하는
구간이 생긴다. 이것이 주된 실패 모드였다.

→ **창(window) 래치 방식**으로 교체:
1. 팔이 빠르게 뻗기 시작하면(`속도 > 1.2 m/s` ∧ `뻗음속도 > 0.45 m/s`) 창을 연다
2. 창(320ms) 동안 **최고 속도와 그 순간의 궤적 방향**을 누적 기록한다
3. 팔이 충분히 뻗은 시점(`뻗음 > 어깨폭 0.95배` **또는** 창 시작 대비 `+0.30배` 증가)에 발사한다

종류 분류도 현재 프레임이 아니라 **최고 속도 순간의 속도 벡터**로 수행하므로,
감속 구간에서 엉뚱하게 분류되지 않는다. 회귀 테스트를 하니스에 추가했다
(`punch split across frames still fires` — 기존 로직으로는 반드시 실패하는 케이스).

**(2) 가드가 펀치를 막고 있었음**

`!guardActive` 조건 때문에 가드 판정 중에는 펀치가 아예 발동하지 않았다.
그런데 **제대로 된 복싱 스탠스는 항상 두 주먹이 얼굴 옆에 있어서 가드 조건을 상시 만족**한다.
자세를 잘 잡을수록 펀치가 안 나가는 역설. → 조건 제거.
가드 중인 팔은 애초에 빠르지도 뻗지도 않으므로 운동학 조건만으로 충분히 걸러진다.

**(3) 양팔 visibility를 AND로 묶어 단일 실패점이 됨**

기존 `wristOK`는 **좌우 팔꿈치·손목 4개 전부** `visibility ≥ 0.5`를 요구했다.
넷 중 하나만 흔들려도 펀치 판정 전체가 정지한다. 빠르게 움직이는 팔은 visibility가 잘 떨어지고,
정면으로 뻗으면 팔꿈치가 손에 가려 자기 가림(self-occlusion)이 생긴다.
→ **팔별로 독립 판정**(`armVis.L` / `armVis.R`)하고, 펀치용 하한을 `ARM_VIS_MIN = 0.3`으로 분리.

`modelComplexity: 1` + 66ms 스로틀(~15fps)에서는 펀치가 2~3 샘플에 불과했다.

자세 지표는 EMA·히스테리시스로 평활되므로 lite의 랜드마크 노이즈에 둔감하다.

**부수 조치 — 시간 상수의 프레임 의존성 제거**

### [09:30] #3 3D Z좌표 펀치 분류 반영 확인

- 펀치 분류 3단계(임계값 12 km/h, 쿨다운 350ms):

  - Z변화 낮음 → 기본(LEFT_JAB / RIGHT_CROSS)
- 글러브 로컬 Z: `gloveZ = -3.5 + depthExt * 8` (팔 뻗을수록 앞으로).
- HUD: `V3D / Z-ext / Z-vel` 값 표시(`moveHud`).

## 📌 얼굴 사진 → 3D 머리 대체 — 타당성 검토 (2026-08-24)

**결론: 가능하지만 "실시간 브라우저"와 "5일" 제약 안에서 3단계 접근을 권장.**

### 요구사항 정리
- 선수 얼굴 사진 몇 장 → 3D 머리로 렌더링 → 아레나/클라이언트 아바타 머리 교체
- 목표: "얼굴이 진짜 그 사람처럼 보이는 3D"

### 옵션 A — 사진을 텍스처로 입힌 구형/박스 머리 (1~2시간, 저난이도) ★추천
- 얼굴 사진을 `THREE.TextureLoader`로 로드해 머리 구(sphere) 또는 직육면체의 **정면 텍스처**로 매핑.
- 현재 `humanoid.js`의 `head`(구)만 텍스처 입힌 구로 교체하면 됨.
- **장점**: 브라우저에서 즉시 동작, 무설치, 5일 안에 확실히 완료.
- **단점**: 정면만 정확하고 측면/뒤가 왜곡됨(2.5D 수준). 완전한 3D 얼굴은 아님.

### 옵션 B — 사진 → FLAME/DECA 3D 얼굴 재구성 → GLB로 내보내기 (1~2일, 고난이도)
- 오프라인 Python에서 DECA(또는 MICA/FLAME)로 단일/다중 사진 → 3D 얼굴 메쉬 + 텍스처 + 표정/립싱 파라미터 복원.
- 결과를 `.glb`로 export → `THREE.GLTFLoader`로 로드해 humanoid `head` 대체.
- **장점**: 진짜 3D 얼굴, CV 과제(단안 3D 복원)로서 **Show Numbers/창의성** 어필 가능. 회전/측면도 자연스러움.
- **단점**: GPU/Python 환경 필요, 사진 정합·조명 보정·GLB 크기 최적화로 시간 리스크 큼. 삼성 사내 적용 시 FLAME 계열 라이선스(MIT/연구용 혼재) 확인 필요.

### 옵션 C — 정면/측면 사진 → 사진 기반 빌보드 + 머리 매핑 하이브리드
- 정면/후면/측면 사진을 받아 머리에 다중 뷰 텍스처 매핑하거나, 카메라를 마주보는 스프라이트 면.
- A보다 낫지만 B보다 못한 중간. 단순성 대비 이득이 크지 않음.

### 권장
- **이번 발표용은 옵션 A로 즉시 확보**하고, 시간이 남으면 옵션 B(DECA 단안 3D 복원)를 **"차별화 포인트 + Show Numbers"**로 추가.
- 옵션 A 구현 포인트: `humanoid.js`에 `setHeadTexture(url)` API 추가 → `TextureLoader`로 구 머리 `MeshStandardMaterial.map` 설정 → 서버 `static/faces/`에 사진 배치.
- 사진 저작권/초상권: 팀원 얼굴은 본인 동의 확보, 외부 인물은 사용 금지.
